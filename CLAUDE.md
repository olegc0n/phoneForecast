# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Lili is a weather display (Yandex forecast + clock) for an always-on Moto G4 Plus (Android 8, WebView ~69), with an animated SVG cat on the forecast screen. `README.md` covers building and usage; `docs/ARCHITECTURE.md` explains the design and the traps behind it. Read the relevant ARCHITECTURE.md section before touching the rig, springs, frame driver or coordinates.

## Commands

No package manager, no dependencies, no test framework. Everything is plain `node` or PowerShell.

```
node tools/build.js [--debug] [--test] [--plandemo] [--nocat] [--noalive]
powershell -ExecutionPolicy Bypass -File tools/build-apk.ps1 [-Install] [-Overlay] [-Test] [-PlanDemo] [-NoCat] [-NoAlive]
```

- `build.js` inlines every `src/` module into one self-contained page: `informer.html`, `android/assets/informer.html`, and `tools/studio.built.html`. All of them are generated and gitignored, so never edit them.
- `build-apk.ps1` runs `build.js` itself, then aapt2 → javac → d8 → zipalign → apksigner. There is no Gradle. Output goes to `android/build/phone-forecast.apk`. It needs JDK 17+ and the Android SDK (`ANDROID_HOME`, default `%LOCALAPPDATA%\Android\Sdk`).

Offline harnesses (each one is a self-contained test suite; run the one that matches the code you changed):

```
node tools/check-weather.js [real.json]   # weather.js: fact vs hourly, staleness, due(), quota logic
node tools/check-wardrobe.js              # wardrobe.js: outfit ladder, night, scene leftovers
node tools/check-settings.js              # settings.js + weather.js: overrides, blanks, request spending
node tools/check-plan.js [--full] [--weather clear|rain|snow|hot|none] [--special] [--json]
```

The first three print PASS/FAIL lines and exit non-zero on failure. `check-plan.js` prints the generated day and does not assert anything. Each harness loads the **real** source files into a `vm` sandbox and fakes only the browser. They never touch the network.

On the device: `adb logcat -s Lili` (the page console and lifecycle trace are piped there). `adb shell am start -n com.lili.informer/.MainActivity -e ep <episode_id>` plays one animation, and `-e plan 1` dumps today's schedule.

## Hard constraints

- **ES5 only, plain globals, no modules.** The target is WebView ~69, so don't use `let`/`const`, arrow functions, template literals or `class`. Each file defines an IIFE global (`var Weather = (function(){...})()`).
- **Load order is the `MODULES` array in `tools/build.js`.** A new `src/` file does nothing until it is added there, in dependency order (`dom` first, `bus` before emitters, `rig` before `anim`, `boot` last). If the studio needs it too, add it to `STUDIO_MODULES` as well.
- **The API quota is 30 requests/day.** Never write code or tests that call the Yandex API to "see what happens". Use `check-weather.js` with a synthetic or captured response. App launches must stay free: `Weather.restore()` sets `lastcall` from the cached file's timestamp. Settings saves only re-fetch when the key or URL actually changed.
- **The API key never goes in git.** The real key and coordinates live in `.local/config.json` (gitignored), and `build.js` substitutes them at build time. `tools/yandex-check.html` holds a key when in use, so don't commit a real one there either.

## Build-time string replacement (fragile, and fails silently)

The config block at the top of `src/informer.base.html` is plain `var` globals. Several things depend on its exact text:

- `build.js` flags and the `.local` override use **exact-string `replace()`** on lines like `var cat_debug         = false;` (column alignment included) and `var api = 'xxxxxxxx-...';`. If you reformat or rename one of these lines, its flag stops working and nothing errors. `--noalive` also matches the literal `Alive.step(dt);` in `cat.js`.
  - Known instance: `--random`/`-Random` targets `var cat_episodes_random = false;`, which no longer exists, so it is currently a no-op. The README also still describes the removed launch chooser (`cat_start_menu`, "Тест анимаций") that the gear/settings dialog replaced.
- The harnesses pull the config by filtering lines that match `/^var [a-z_]+ *=/`. Config globals must stay unindented, one per line, with lowercase/underscore names.
- `cat_build` is stamped by the build, and a saved day plan from a different build is discarded.

`src/core/settings.js` overlays four of these globals (`api`, `api_url`, `cat_quiet_from`, `cat_quiet_to`) from localStorage at boot. Phone-side values beat build defaults, and a stored blank falls back to the default. It mutates the globals in place, and every module reads them directly.

## Architecture

**Two halves that only meet on `Bus`** (`src/core/bus.js`):
- `src/core/`: the forecast. It is started first and unconditionally in `boot.js` (`Settings.load` → `Weather.restore` → `Clock.start`). It must never reference the cat.
- `src/cat/`: Lili. `Cat.init()` and `SettingsUI.init()` run inside `Guard.run`. Three faults within one minute disable the cat for the session, and the clock carries on. Anything optional or cat-related goes through `Guard`.
- `Bus.on(topic, fn, replay)` keeps the last payload per topic. Weather is published as *state*, so a subscriber that arrives late (the cat starts after the forecast paints) must pass `replay` to receive it.

**Weather** (`weather.js`) stores the whole raw API response. While the response is fresher than `timeout` it shows `fact`; after that it shows the hourly entry for the current hour (up to 48 h ahead). `Clock`'s minute tick calls `Weather.rehour()` and `Weather.due()`. `Weather.status()` → `fact | hour | stale-fact`, and only `stale-fact` counts as a real failure.

**Cat layers, bottom up:** `rig.js` (pose) → `anim.js` (timer-driven frame loop, five fps tiers, *not* rAF) → `alive.js` (springs/micro-motion) → `actions.js` (verbs) → `beats.js` (beat vocabulary, cursor-timed) → `scenes.js` (animations as data) / `episodes.js` (17 legacy hand-written animations plus the weighted picker) → `plan.js` (the whole day planned at 00:00) → `cat.js` (the one life loop; also `Cat.play/plan/home/back`, which `MainActivity.java` calls through `evaluateJavascript`, so keep those names stable).

Key rules from ARCHITECTURE.md that are easy to break:
- `Rig.set` writes the authored `pose` channel and `Rig.bias` writes the procedural `add` channel. Anything that runs every frame uses `bias`.
- The rig owns each animated part's whole `transform` attribute. A static offset on an animated `<g>` gets wiped on the first frame, so put it on an outer wrapper group.
- Morphed parts must be registered in `Rig.PARTS`. Every shape in a `shapes.js` set uses identical path commands in the same order.
- Coordinates are **percent of `#cat_stage`**, never `vw` or px (`window.innerWidth` is wrong on this page). Props stay below 63% of the stage height, because nothing may cover the clock.
- Instant repositions must call `Alive.settle()`, or the springs read them as speed.

**New animations** go in `src/cat/scenes.js` as data (`Scenes.add(id, {tags, when, weight, beats, perDay?})`), not in `episodes.js`. `tools/studio.html` (built to `studio.built.html`) previews them. Run `check-plan.js` afterwards to see where the scene lands in the day.

**Android host** (`android/`): two framework-only Java files, no AndroidX. It loads `file:///android_asset/informer.html` and needs `setAllowUniversalAccessFromFileURLs(true)`, or every XHR is blocked as a null-origin CORS failure. The JS bridge is `window.PhoneForecast`, feature-detected in `host.js`, so the same page also runs in a plain browser tab. Text files are LF except `*.ps1` (CRLF), as set in `.gitattributes`.

## Live wallpaper variant (branch `screensaver`)

A second app, **Lili** (`com.lili.wallpaper`): an Android `WallpaperService` that puts the cat on the user's own home screen, over a native backdrop: **My wallpaper** (the user's own wallpaper picture, kept for good as `files/original.jpg`), one of six dark presets, or a photo. The workflow is: edit the look in settings, **Preview**, choose **Home screen** / **Lock screen** in the preview, **Apply**. Settings shows only a read-only status line ("Lili is on: home screen"...). The preview's two switches are a **plan** that Apply carries out through `SettingsActivity`. **Home** on saves the current wallpapers of both screens (`Backup.beforeHome`), then opens the system picker. Home off puts them back, else My wallpaper, else asks. **Lock screen** can't be turned on: Android has no API for animating the lock screen. She is animated there only where the vendor shows third-party live wallpapers (stock Android, "Home screen and lock screen" in the picker; not Huawei, Samsung, most Xiaomi/Oppo). The switch shows that state, disabled. A still lock-screen picture (`LockPicture`/`LockJob`, `#still=1`) was built and works on Huawei, but it is **blocked**. Nothing may set `lock_on` true (group I fails if anything does), and the code stays for a phone that still has lock mode from an earlier build (the switch is then enabled only to turn it off) and for the feature to come back. The preview puts an icons layer over her: drawn mock icons, or the user's real home screen captured with MediaProjection while the wallpaper is chroma-keyed magenta. No clock, no weather, no network and no key. It has six permissions: `SET_WALLPAPER`, `RECEIVE_BOOT_COMPLETED`, `READ_EXTERNAL_STORAGE` up to API 32, `MANAGE_EXTERNAL_STORAGE` (All files access, Android 13+, for My wallpaper only; Play would reject it, and distribution is GitHub), `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PROJECTION` (the capture). The design and the reasons behind it are in `docs/WALLPAPER.md` (sections 8 and 9), and the release-notes draft is `docs/WALLPAPER-RELEASE.md`. (`docs/SCREENSAVER.md` is a stub; the earlier screen-saver design is in git at `e9db05a`.)

```
node tools/build-wallpaper.js [--debug]      # wallpaper.html + android-wallpaper/assets/wallpaper.html
node tools/check-wallpaper.js                # groups A-I: sky, shuffle, Plan stand-in, contract, built files + manifest, whole page, timer gate, still mode, settings + preview + mock-icon colours, strings, the draft and plan, My wallpaper never deleted, chroma always ended
powershell -ExecutionPolicy Bypass -File tools/build-wallpaper-apk.ps1 [-Install] [-Overlay] [-Release]
adb shell am start -n com.lili.wallpaper/.PreviewActivity [-e ep <episode_id>]   # the applied look, no buttons
adb shell am start -a android.service.wallpaper.CHANGE_LIVE_WALLPAPER --ecn android.service.wallpaper.extra.LIVE_WALLPAPER_COMPONENT com.lili.wallpaper/com.lili.wallpaper.LiliWallpaper
```

- **Edit nothing shared.** No file under `src/`, `android/` or `tools/` that exists on `main` is edited or deleted on this branch, and neither is `README.md`. Everything the wallpaper needs is additive: `src/wallpaper/`, `src/wallpaper.base.html`, `android-wallpaper/`, `tools/wallpaper-modules.js`, `tools/build-wallpaper.js`, `tools/build-wallpaper-apk.ps1`, `tools/check-wallpaper.js`. That is what lets `main` keep merging in with no conflicts.
- The module list is derived from `MODULES` in `tools/build.js`: `src/wallpaper/timers.js` first, before anything else; `cat/plan.js` replaced by `src/wallpaper/sky.js`, `shuffle.js`, `plan-random.js`; and the tail `wall-tick.js`, `still.js`, `wall.js`, `wall-boot.js`. The `cat_*`/`app_*` config and `#cat_` CSS are extracted from `src/informer.base.html` at build time. A new `scenes-*.js` on `main` is bundled automatically.
- `cat.js` is driven only through what it already exposes: a stand-in `Plan`, a synthetic payload on Bus topic `weather` (`Sky`), the `minute` topic (`WallTick`) and `Cat.play(id)`. Quiet hours are fixed in the page config (`23:00`-`07:00`), and `Wall` never calls `Cat.play` inside them: it would wake her body without clearing `cat.js`'s `quiet` flag.
- **Timers are gated per page.** `timers.js` replaces `window.setTimeout/clearTimeout/setInterval/clearInterval`; `Timers.freeze()` holds every pending timer and `Timers.thaw()` re-arms it with the time it had left, so a hidden wallpaper has zero wake-ups. Never `WebView.pauseTimers()`: it is process-wide, and the picker's preview engine, the real engine and the preview activity share one process. Group D fails if shared code uses `requestAnimationFrame` or keeps a reference to a native timer function.
- The engine drives the page with `Wall.show()`, `Wall.hide()` and `Wall.apply({size, lift})`. A show after 10 s or more out of sight starts a fresh animation (nothing in the sleep window; an animation frozen half-way finishes first). Size and height are px set by `Wall.place()`: the 9:16 stage scaled to `size`% and lifted `lift`% of the screen height, inside `#wl_view`, which clips and fades props entering from outside the stage.
- **The lock-screen picture is the same page in still mode** (`wallpaper.html#still=1`, `src/wallpaper/still.js`). `wall-boot.js` runs `Still.begin()` instead of `Wall.begin()`, and `Wall.show/hide` do nothing. She gets one calm pose (asleep in the sleep window) and no scene. When every tween has finished (2.2 s at the latest, which is before `cat.js`'s first beat), the page calls `Timers.freeze()` and `PhoneForecast.stillReady(json)`. `LockPicture.java` renders that page offscreen (a private `VirtualDisplay` on an `ImageReader`, with a `Presentation` holding `LiliView.still()`), copies the frame, tears everything down within 8 s, and calls `setBitmap(..., FLAG_LOCK)` on a worker thread. `LockJob` (a persisted `JobService`, every 3 h) and each Apply of a new look (one `LockPicture.requestSoon` from `commit()`) refresh it while lock mode is on. An automatic refresh never overwrites a lock wallpaper the user changed: when `getWallpaperId(FLAG_LOCK)` differs from the stored `lock_id`, it turns lock mode off. Blocked in this version (above). Design, the decision and the untested platform assumptions: `docs/WALLPAPER.md` section 8.
- **Where Lili lives is the system's state, never a stored choice** (`getWallpaperInfo()`, `getWallpaperId(FLAG_LOCK)` against `lock_id`, `getWallpaperInfo(FLAG_LOCK)` on API 34+), re-read on resume and after every action: a read-only status line in settings. The settings screen hands the lock state and its line to the preview (`EXTRA_LOCK_STATE`/`EXTRA_LOCK_NOTE`), whose switches are set with the listener detached. **The preview's switches are a plan**: Home starts on when Lili isn't the home wallpaper yet, Lock is blocked as before, and nothing acts until Apply. `SettingsActivity.previewed()` commits the look, then carries out the differences: Lock off first, then Home on/off (`continuePlan` after the restore or its dialog). `Backup.java` saves both screens on every Home turn-on (replacing older copies, except when the screen is already Lili's; unreadable = no backup), and Home off restores them on a worker thread under `Backup.WRITE`. With no home backup it restores My wallpaper (`Backup.ORIGINAL`). With nothing at all, the app's own dialog offers a photo, the system default or Cancel. `Prefs.migrate()` turns the three-button build's `where` into `lock_on`.
- **Colours come only from named constants**: the settings screen's and the preview's in `SettingsActivity`, the mock icons' in `IconsView`. EMUI drew the theme's `Button` white under white text. Every `TextView`/`Button`/`Switch`/`SeekBar` is made by one factory (`static text()/button()/toggle()`, private `slider()`) that sets its text colour and background. The preview's buttons are `paint(b, primary, true)` (opaque faces, a 2 dp `OUTLINE` that reads over white, black and every preset), and its panel is `panelOverBackdrop()` (opaque `PANEL`, the same outline). The settings screen is opaque (`LiliSettings` is `Theme.Material.NoActionBar`, the window and bars `PANEL`); nothing shows through. Group I checks WCAG contrast of every pair (the mock's fills 3:1 over white, black and every preset, its labels 4.5:1), and fails on any other colour source, view alpha, `AlertDialog`, control made outside its factory, a preview button not painted for a backdrop, alpha in `PANEL` or a button face, or a wallpaper theme. A new colour means a new constant and a new pair in group I.
- **The look is a draft until Apply.** Background (`Look.kind`: `preset`/`photo`/`original`), photo, darkening, size and height are a `Look` (immutable) held by `SettingsActivity`. **Preview** shows it full screen (`PreviewActivity` with `Look.EXTRA`, a `LiliView` given that `Look`: backdrop and boot config from it, no prefs listener), and its **Apply** returns it with the plan for `SettingsActivity.commit()`, the only writer of `bg_*`/`size`/`lift` (`Look.toPrefs`, one `apply()`; group I fails on any other). Cancel/Back keep the draft and drop the plan. Back with changes asks Apply / Discard / Keep editing; a fresh open starts from prefs. A picked photo goes to `files/bg_draft.jpg` and is renamed over `bg.jpg` on Apply (`bg_rev` + 1); `Backdrop` keeps one decode per file and revision (a third slot for `original.jpg`, keyed by `orig_at`), so the wallpaper never shows the draft photo and the preview never the old one. Before the first Apply (no `bg_kind`) the applied look is My wallpaper once it is kept; every Apply writes `bg_kind`, so a later My wallpaper never overrides an applied look.
- **My wallpaper is never deleted.** `Original.obtain()` (settings, every open/resume until it works) keeps the current home picture: from the static home backup if Lili is the wallpaper, nothing if another app's live wallpaper, else read with `READ_EXTERNAL_STORAGE` (API ≤ 32) or only with All files access (`isExternalStorageManager()`, API 33+, from a card with **Allow** / **Pick from photos instead**). It goes through `Backdrop.importPhoto` into `original.part`, which is renamed to `original.jpg` only if that is absent. Nothing deletes, renames over, imports into or writes `original.jpg`, and nothing uses `deleteFile`/`listFiles`; group I checks it statically. `orig_at` is written only by `Original`.
- **The capture never leaves chroma on.** `CaptureActivity` (transparent, its own task; the preview then `moveTaskToBack(true)`) gets consent, starts `CaptureService` (foreground, `mediaProjection`) on API 29+ before `getMediaProjection()` (Android 10+ refuses it otherwise with targetSdk ≥ 29), and registers the projection callback before `createVirtualDisplay`. `Chroma.set(true)` makes the engines' views draw `#FF00FF` and hide the WebView. One frame is taken, then `release()` ends everything, with `Chroma.set(false)` in its `finally`. A 5 s safety timeout, every failure and `onDestroy` go through it (group I checks it). `Keyer` (plain Java) cuts the magenta out (g, \|r−b\| ≤ 0.15·max(r, b), soft edges solved against the foreground), and `HomeShot` saves `homescreen.png` with the screen size. The preview uses it only while the size matches.
- Applied settings travel by `SharedPreferences` (file `lili`): `commit()` writes it, every `LiliView` that follows prefs and every engine listens. `bg_*` (and `orig_at`, when My wallpaper is first kept) repaints the native backdrop, `size`/`lift` go to the page as `Wall.apply`, with no reload, each once per Apply (listeners coalesce the keys). Listeners are held weakly, so their owners keep strong references.
- `build-wallpaper.js` never reads `.local/config.json`, and it fails (exit 1, nothing written) when an expected marker, CSS rule or SVG attribute is missing, when the page would mention the forecast API, when the screen saver's `#sv_clock` is back, or when `timers.js` is not the first module.
- The application id is `$AppId` in `tools/build-wallpaper-apk.ps1` (passed to `aapt2 link --rename-manifest-package`), and it equals the manifest's `package` and the Java package, `com.lili.wallpaper`; group E asserts that they agree. The version is `android-wallpaper/VERSION`. The platform must be API 34+ (`getWallpaperInfo(int)`, `WallpaperColors`); `minSdk` stays 21, with every newer call behind `Build.VERSION.SDK_INT`. d8 gets the classes as one jar, because a list of `.class` paths overflows cmd.exe's command-line limit. Debug builds are debuggable (for `run-as`). `-Release` needs `.local/release.keystore` plus `LILI_KS_PASS`/`LILI_KEY_PASS` (and optionally `LILI_KEY_ALIAS`). It never creates a keystore.

**After every merge from `main`:** `node tools/check-scenes.js && node tools/check-wardrobe.js && node tools/check-wallpaper.js`, then `node tools/build-wallpaper.js`. A failure in `check-wallpaper` groups D, E or F means `main` changed something the wallpaper leans on. Fix it in `src/wallpaper/`, not in the shared file.
